# e2e

## Purpose

Playwright end-to-end smoke tests, run against a real local Supabase (not mocked) — covers what the mocked unit/component tests can't (RLS, the `proxy.ts` auth guard, the full order lifecycle including payment).

## Contents

- `auth-guard.spec.ts` — exercises `src/proxy.ts` → `updateSession`: an anonymous visitor hitting `/dashboard` or `/onboarding` must be redirected to `/login`. Needs only a booting app, no seed data.
- `smoke.spec.ts` — public smoke: the landing page renders its "Live booth ordering" hero heading, and `/login` renders its "Continue with Google" button. Needs only a booting app, no seed data.
- `customer-order.spec.ts` — the customer checkout against the seeded "Kopitiam Cart" booth (`c0ffee01-0000-4000-8000-000000000001`, entered via short code `e2eKopitiam01`): open the booth, customize a drink, place an order under a name, land on `/order/<booth>/pay?t=<token>`, which redirects to the stub pay page the Payment mock serves, tap "I've paid" there, and come back. The return gives the order its number and redirects to `/order/<booth>/<orderNumber>?t=<token>`, showing "payment sent" while vendor acceptance is pending. Requires `supabase/seed/coffee-cart.sql`. The pay panel calls paykit's `/api/v1/checkout*` HTTP API through `src/lib/paykit/client.ts`; this suite uses the Payment mock below. It does not test a vendor's complete acceptance/preparation/completion lifecycle.
- `order-code.spec.ts` — short-code order entry: a valid code (`e2eKopitiam01`) renders the booth's order page ("Kopitiam Cart", a visible "Customize" button); a bogus code hard-blocks with an "this code expired" message. Also requires the coffee-cart seed.
- `vendor-fulfillment.spec.ts` — the board's fulfillment path for one order, end to end: a customer orders and pays on the seeded booth (`placeClaimedOrder`), then a vendor signed in as the booth's owner opens `/dashboard`, finds that order's ticket and taps "Mark paid & start" (a claimed payment folds confirm and start into one tap), "Mark Ready" and "Mark Picked Up", waiting out the board's 4s undo window between steps. Meanwhile the customer's status page (it polls every 5s) turns to "It's ready" and then "Collected. Enjoy!", and the booth's TV screen (`/order/<booth>/display`) shows the number under "Ready for pickup" and drops it after pickup. Every board lookup is scoped to this order's ticket (by its "More actions for order #N" menu), since other specs leave their own orders on the same board; so it checks the ticket leaves, not the board-wide "All caught up". Requires the coffee-cart seed and `supabase/seed/e2e-merqo-stub.sql`. Batch select, "Mark all ready" and bump are not covered.
- `csp.spec.ts`: in CI (production build) `/` and `/login` serve a nonce CSP with nonced scripts and no violations.
- `signed-in-smoke.spec.ts`: `renderSmoke` over every dashboard and admin page as the seeded vendor made an admin and cleared through TOTP; a password-only admin session is sent to `/mfa`. Needs the coffee-cart seed.
- `totp.ts`: not a spec; RFC 6238 code generator used by `vendor-auth.ts` (`signInSeedVendor(..., { asAdmin: true })`).
- `customer-flow.ts` — not a spec; the seeded booth's id and short code, and `placeClaimedOrder(page, name)`: the customer checkout through the paykit stub and back to the status page, returning the order number the page shows. Shared by `customer-order.spec.ts` and `vendor-fulfillment.spec.ts`.
- `vendor-auth.ts` — not a spec; `signInSeedVendor(context, baseURL)` signs a browser context in as the seed booth's vendor (`6df824a1-...`). The seeds give that user no password, and locally it can be a developer's real account, so nothing sets one: the service-role key mints a magic-link token, `@supabase/ssr` redeems it, and the auth cookies it writes go into the browser context. It also writes a fresh `legal_check_state` row (the legal gate otherwise asks merqo, which e2e cannot reach, and fails closed) and marks both dashboard tours seen. It reads `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` from the runner's environment and refuses any host but `127.0.0.1`/`localhost`.
- `paykit-mock.ts` — not a spec; a tiny `http.createServer` stand-in for paykit's checkout/claim/confirm endpoints (see Payment mock below).
- `global-setup.ts` — Playwright `globalSetup`: starts `paykit-mock.ts` and returns its shutdown as the matching teardown.

## Connectivity

Run via `pnpm test:e2e` (auto-starts `pnpm dev`); `auth-guard.spec.ts` and `smoke.spec.ts` need only a booting app, `customer-order.spec.ts` and `order-code.spec.ts` need the coffee-cart seed applied first (Docker + `supabase start` + migrations + `supabase/seed/coffee-cart.sql`). `vendor-fulfillment.spec.ts` also needs `supabase/seed/e2e-merqo-stub.sql`, and the three Supabase variables above in the runner's own environment (Playwright passes them on to `pnpm dev`); export them from `supabase status -o env` with the same `--override-name` mapping CI uses. The booth id and short code live in `customer-flow.ts` (`order-code.spec.ts` still has its own copy); keep them in sync with the seed file. Locally the dev server runs on port 3000, in CI the production build does; set `E2E_PORT` to use another when 3000 is taken (the paykit mock's callback follows it).

## Payment mock

qkit's checkout flow calls paykit's real HTTP API (`src/lib/paykit/client.ts`), and no paykit deployment runs alongside e2e (locally or in CI). `global-setup.ts` starts `paykit-mock.ts` — a small `http.createServer` implementing `POST /api/v1/checkout`, `GET /api/v1/checkout?order_ref=`, `GET /pay/:id` and `POST /pay/:id/claim` (the stub pay page: one "I've paid" button that claims the transaction, posts the callback and redirects to the `return_url` qkit sent; no screenshot is taken), `POST /api/v1/checkout/:id/confirm`, `GET /api/v1/checkout/:id/evidence`, and `GET /api/v1/checkout/:id` with paykit's real response shapes (always returns a PayNow-style `type: "qr"` checkout with `status`, and a `pay_url` to the stub page when a `return_url` was sent, deduped per `order_ref` the same way paykit dedupes on `(kit_slug, order_ref)`, and echoing the `expires_at` qkit sent, keeping the first value on a replay as paykit does) — on a fixed local port. `playwright.config.ts`'s `webServer.env` points `NEXT_PUBLIC_PAYKIT_URL`/`PAYKIT_KIT_SECRET` at it, so `pnpm dev`'s server-side paykit calls land on the mock instead of a network call. This only covers the checkout/claim/confirm surface these specs exercise — `GET /api/v1/vendors/{id}/config` (which kind of payment a vendor has on file, read by the booth form) has no e2e coverage and isn't mocked; qkit no longer writes that config at all. The mock also posts paykit's payment-status callback to qkit's own `POST /api/paykit/payment-status` after a claim or a confirm changes a transaction, authenticated with `PAYKIT_CALLBACK_SECRET` from the same `webServer.env`, so the customer's return and the callback hit one order together as they do in production. The mock does not check `return_url` against a registered origin; paykit's own tests cover that.
