# dashboard

## Purpose

The authenticated vendor area — a shared header/nav shell wrapping the live order board plus sub-routes for booth management, order history, billing, account, board preferences, analytics, and support.

A second test asserts the structural precondition for sticky positioning: the header's immediate parent carries both `contents` and `print:hidden` classes (jsdom doesn't compute layout, so it can't prove the header actually sticks on scroll, but it can prove the wrapper isn't a plain box that would break the containing block).

Renders `DashboardNav` inside a `contents print:hidden` `<div>` — not a `<header>` wrapper, since `@merqo/ui`'s `DashboardNav` already renders its own sticky/bordered `<header>` internally. `contents` is load-bearing, not decorative: `@merqo/ui`'s inner `<header>` is `position: sticky`, so a plain wrapper `<div>` (no `contents`) would itself become the header's containing block at exactly the header's own height, leaving it no room to stick; `display: contents` removes the wrapper's own box so `<header>` becomes a direct flex item of this component's `min-h-screen flex flex-col` container instead, restoring the pre-migration containing-block structure. `print:hidden` still applies under `@media print` regardless of the wrapper's own `display` value. Plus a `signOut` server action, and `DashboardTour` (per-page onboarding tours, gated on `vendor.tours_seen`).

  exact conditional writes, Paykit response state, payment isolation on pickup

- `order-actions.ts` — validated vendor actions using the authenticated client
  and RLS. `advanceOrder` and `revertOrderAdvance` condition writes on the expected
  status and modify only fulfillment state/timestamps; the ready transition sends
  best-effort customer notifications unless the vendor opts out.
  `confirmOrderPayment` and `confirmPaymentAndStart` confirm through Paykit before
  mirroring its confirmed state. The merged action also starts the order; its undo
  only restores fulfillment status, preserving payment. `confirmOrderPayment`
  logs a local mirror failure but reports Paykit's confirmation as successful;
  reliable reconciliation after that failure remains outstanding.
  Cancellation rejects confirmed payments and manually closed orders, while
  allowing unpaid auto-completed orders. `bumpOrder` changes queue priority;
  ready/abandoned sweeps affect only eligible orders in the vendor's RLS scope.
  `restoreAutoCompleted` restores only sweep-completed orders, restamping ready time.

Terminal cards remain visible during fulfillment undo. New-order alerts, desktop notifications, tickets and the walk-up dialog use the same daily display number. The event dialog auto-opens only for an active event booth. Board state does not confirm payment; settlement uses explicit Paykit-backed actions.

- `walkup-actions.ts` — `placeWalkupOrder(boothId, input: PlaceOrderInput, paid: boolean)` server action: validates `input` with the same `placeOrderSchema` the customer cart uses, then calls the `place_walkup_order` RPC (migration 0061, originally 0060) with `p_booth_id`/`p_customer_name`/`p_items`/`p_paid`. `paid` lets staff mark payment as already collected at the counter in the same step as placing the order; the RPC ignores it for a booth that doesn't take payment. Maps its RAISE-prefixed errors to vendor-facing messages (mirrors `o/[code]/actions.ts#messageFor`, minus the customer-only `ORDER_EXPIRED`/`ORDER_UNSERVABLE` cases, since a walk-up order isn't gated by the booth's schedule).
- `walkup-menu-actions.test.ts` — vitest suite (mocked Supabase chain + `rpc`) covering `getWalkupMenu`'s invalid-id short-circuit, the RLS-scoped not-found → null, the happy path (parsed menu items + `booth_remaining_stock` result + `expectsPayment`/`paymentKind`), a configured-payment-kind case, the stripe-is-dark case, and dropping a malformed menu item entry.
- `walkup-menu-actions.ts` — `getWalkupMenu(boothId)` server action: reads a booth's `menu_items` and `payment` config (RLS-scoped to the caller's own booths, same as the booth-edit page) plus its live `booth_remaining_stock` RPC result, for `WalkupOrderDialog` to render. Also derives `expectsPayment`/`paymentKind` from the booth's payment marker via `paymentKindOf`/`expectsPayment` in `@/lib/payment-marker` (a live, non-stripe kind counts; stripe is reserved but dark, same rule `place_walkup_order` applies) — reads just the `kind` discriminant rather than `parsePaymentConfig`'s full-shape parse, since `booths.payment` now stores only the minimal `{kind}` marker the paykit cutover writes (see `booths/actions.ts`), which the strict parse would reject outright. Unfiltered by `available`: same as the customer flow, an unavailable item is rejected server-side rather than hidden client-side.
- `walkup-order-dialog.dom.test.tsx` — RTL tests for `WalkupOrderDialog`: fetches the selected booth's menu once opened, adds a plain item and submits (asserts the exact `placeWalkupOrder` call including `paid=false` + dialog close), the payment-collected switch appearing only when the booth expects payment and its state reaching `placeWalkupOrder`'s third argument, a no-booths empty state that skips the fetch entirely, and the disabled-submit-with-empty-cart state.
- `walkup-order-dialog.tsx` — Staff build an order from the selected active booth's menu, then handle payment after placement. Explicit confirmation uses Paykit; leaving payment for later preserves an unpaid ticket. Event booths clear the dialog for the next customer, while other booths close it. Menu request identities discard stale responses. Server actions and SQL recheck ownership, stock and limits independently of the displayed menu.

## Connectivity

`layout.tsx` gates every route under `/dashboard` (auth/vendor/admin/legal-acceptance redirects) and renders `dashboard-nav.tsx` around `{children}`; `page.tsx` is the `/dashboard` index route and renders `realtime-order-board.tsx`, which calls the order-mutation actions in `order-actions.ts` indirectly via `OrderCard` and subscribes through `@/hooks/use-realtime-orders`. `dashboard-nav.tsx` links out to `completed/`, `booths/`, `plan/`, `profile/`, `settings/`, `stats/`, `feedback/` — the dashboard's sub-routes for order history, booth management, billing, account, board preferences, analytics, and support respectively. `tour-actions.ts` is called by `DashboardTour` (in `@/components`) once the tour completes. `proof-actions.ts` is called by `PaymentProofViewer` (`@/components/board/payment-proof-viewer.tsx`), the OCR + duplicate-photo hint `OrderCard` opens on a claimed order's proof photo — not from anywhere else in this tree.

## Current board and walk-up controls

Select all targets eligible preparing orders. While tickets are being ticked the filter-and-batch row is pinned to the top of the screen, a tap anywhere on a ticket ticks it (its own buttons still do their own job), and the toast for a batch carries an Undo that walks every moved order back one step with `revertOrderAdvance`. On a phone the Incoming/Accepted switch is a pair of 44px pressed-state buttons, and the settings gear is left to the navigation. The customer-screen dialog opens the public booth display. Walk-up entry places the order before its optional payment step; collecting payment calls explicit Paykit-backed confirmation. Stale-order sweeps update fulfillment state independently of payment settlement.
